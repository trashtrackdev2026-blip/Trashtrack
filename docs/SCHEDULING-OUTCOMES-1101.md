# Scheduling and collection outcome updates — November 1, 2026

New event and collection scheduling uses Asia/Manila time. Past calendar days and elapsed start times today are rejected by both the forms and authenticated server routes. Date/time bounds refresh while a form is open and on returning to its tab. Future dates have no booking horizon. Event end times must follow their start on the same date.

The rules cover collection publication, event publication, draft dates/times, event editing and reactivating a dated collection. Incomplete drafts can omit scheduling; expired drafts must be corrected before publication. Certificate settings cannot backdate an upcoming event. Completed-event certificate corrections and recording actual historical collection outcomes remain possible. Calendar browsing, report history and analytics filters still allow past dates.

Saving a changed collection outcome or its follow-up notes creates a new `schedule` notification in the same transaction as the outcome, audit entry and date reservation. Its audience comes from the saved collection, never the request's proposed recipients. Notices include the actual date/day, AM/PM time, outcome and bounded notes. The existing resident inbox listener and Android FCM display path already support this schema, so no APK update is needed.

The dashboard supplies a stable change ID and expected outcome revision. Repeated requests reuse the saved notice, stale edits are rejected, and unchanged saves create no notification. Phone delivery occurs after commit. A delivery failure leaves the saved outcome and inbox notice intact and returns a visible pending-delivery message. Announcements retains its existing delivery retry controls and automatic outbox recovery while open.

Verification: 149 regression tests passed, including real route handlers with isolated in-memory transactions and the actual phone-payload builder. Cases include yesterday, earlier/current minutes today, Manila midnight, AM/PM, an expiring draft, late retries of committed publications, all outcome statuses, historical results, targeted versus municipal audiences, stale/revoked requests and failed phone delivery. TypeScript, changed-source ESLint, the production build and function-bundle checks passed. The installed framework displayed its existing security upgrade recommendation on the first completed build; the subsequent build passed. No dependency versions changed. No test created a production schedule/event/report or broadcast a notification.

Source is mirrored in `admin-dashboard` and `trashtrack-web`. Existing installations can consume the update once the dashboard/server is deployed. Refresh an already open dashboard tab to load the new outcome save fields. No Firebase rule change or data migration is required.
